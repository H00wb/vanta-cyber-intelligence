2. KENDİ ORTAMINDA ÇALIŞTIRMA

Node.js 24.x gerekir. Proje klasöründe:

  npm ci

.env.example dosyasını .env.local olarak kopyalayın. Kendi projenize ait
NEXT_PUBLIC_SUPABASE_URL ve NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY değerlerini girin.
Yeni Supabase projesinin SQL Editor'ünde sırayla uygulayın:

  supabase/migrations/20261007212753_vanta_requests.sql
  supabase/migrations/20261008000924_vanta_admin_read_access.sql

Daha önce uygulanmış migration'ı tekrar çalıştırmayın. CLI kullanıyorsanız
supabase link ile doğru projeyi bağlayıp supabase db push çalıştırabilirsiniz.

Yönetim ortamını hazırlayın:

  node scripts/setup-admin.mjs

Yardımcı, demo kullanıcıyı, scrypt parola özetini, oturum imzalama anahtarını
ve ayrı DB okuma token'ını .env.local'a yazar:
ADMIN_USERNAME, ADMIN_PASSWORD_HASH, ADMIN_SESSION_SECRET, ADMIN_DB_READ_TOKEN.
Üretilen .test-results/admin-access.sql dosyasını migration'lardan sonra
SQL Editor'de uygulayın; veritabanına token'ın yalnız SHA-256 özeti gider.
Bu ortam değerlerini, yerel SQL çıktısını ve oturum çerezlerini paylaşmayın.
Supabase service-role anahtarı kullanılmaz.

  npm run dev

Yerel adres: http://127.0.0.1:5173

Üretim davranışını kontrol etmek için:
  npm run build
  npm run start

Yerel uygulama da ayarladığınız gerçek Supabase'e yazar. Testlerin gerçek
kayıt oluşturduğunu dikkate alın; yalnız kurgusal veri kullanın.

75 Node ve 21 tarayıcı testinin ayrı ayrı açıklaması TEST_SONUCLARI.md içindedir.
Ekran görüntülerini CANLI_DOGRULAMA.md üzerinden inceleyebilirsiniz.

4. ALAN VE API TESTLERİ NEYİ KONTROL EDİYOR?

tests/request.test.mjs içindeki mevcut senaryolar:

- Dört hizmet değeri kabul edilir; kenar boşlukları temizlenir ve e-posta
  küçük harfe çevrilir.
- Şu 13 geçersiz örnek ayrı ayrı sınanır: boş isim, 101 karakter isim,
  hatalı e-posta, fazla uzun e-posta, NUL içeren e-posta, bilinmeyen hizmet,
  kısa açıklama, 2001 karakter açıklama, isimde kontrol karakteri,
  açıklamanın sayı olması, geçersiz UUID, tek emoji isim ve on emoji açıklama.
  Beklenen: 422, ilgili alan hatası, depo açılmadan ret ve sıfır kayıt.
- İki emoji isim/20 emoji açıklama ile 100 karakter isim/2000 karakter
  açıklama sınırları kabul edilir.
- null, dizi, metin, boş nesne veya eksik alanlı gövde reddedilir.
- Yeni kaydın 201 yanıtı, test deposundaki dört alan ve zamanla eşleşir.
- Depo işlemi bitmeden API başarı dönmez.
- Depodan null, eksik yanıt, yanlış kimlik veya yanlış türde replayed
  gelirse başarı oluşmaz; 503 döner.
- Aynı kimliğin üç eşzamanlı gönderimi bir satır bırakır:
  bir 201 ve iki 200 beklenir. Bu test SQLite sözleşme testidir.
- Aynı kimlikle değişen içerik 409 alır; ilk satır korunur.
- SQL/HTML benzeri açıklama çalıştırılmaz; aynen veri olarak saklanır.
- Depolama hatası 503 verir; iç hata veya başarılı kayıt kimliği sızmaz.
- Bozuk JSON 400, yanlış içerik türü 415, farklı origin 403 alır.
- 16 KiB gövde sınırı Content-Length olmadan da gerçek byte sayısıyla uygulanır.
- GET 405 alır; talep verileri okunamaz.
- Yanlış HTTP durumlu, eksik veya farklı kimlikli yanıt başarı sayılmaz.
- Geçici SQLite dosyası kapatılıp açılınca test kaydı korunur. Bu, gerçek
  PostgreSQL kalıcılık kanıtının yerine geçmez.
- Next.js/proxy ortamında dış Host ve forwarded HTTPS Origin kabul edilir;
  yabancı Origin yine reddedilir.

5. SUPABASE BAĞLANTISI TESTLERİ NEYİ KONTROL EDİYOR?

tests/supabase-store.test.mjs taklit fetch kullanır:

- RPC'ye yalnız bir HTTPS POST gider; beş argüman, apikey, JSON içerik türü,
  no-store ve zaman aşımı sinyali doğru taşınır.
- Tekrar kayıt sonucu yeni kayıt gibi değiştirilmez.
- 409, tanımlı kimlik çakışması hatasına çevrilir.
- 400/401/403/503 iç veritabanı ayrıntısını kullanıcıya taşımaz.
- Yanlış, eksik veya başka kimlikli JSON kaydı doğrulayamaz.
- Boş, bozuk veya HTML biçimli 200 yanıtı başarı sayılmaz.
- Gövdesiz 204 de kayıt doğrulaması değildir.
- Ağ hatası ve iptal/zaman aşımı başarılı depo sonucuna dönüşmez.
- Geçersiz Supabase adresi veya boş anahtar ağ çağrısından önce reddedilir.

7. TARAYICI SENARYOLARI NEYİ KONTROL EDİYOR?

e2e/site.spec.ts içindeki form ve sayfa kontrolleri:

- 320, 390, 768 ve 1440 px genişliklerde başlık/CTA/form görünür; yatay taşma yoktur.
- Geçersiz alanlar POST başlatmaz; odak ilk hatalı alana gider.
- Gönderiliyor durumunda tekrarlayan tıklama yeni istek başlatmaz.
  Gerçek 201 yanıtından sonra doğru kayıt kimliğiyle başarı gösterilir.
- Simüle edilen 503'te alanlar korunur ve başarı gösterilmez.
- Offline gönderimde alanlar korunur; bağlantı dönünce değişmemiş talep
  aynı UUID ile tekrar denenir.
- HTML hata yanıtında anlaşılır mesaj görünür; JSON parser ayrıntısı görünmez.
- HTTP 200 dönse bile yanlış kayıt kimliği başarı sayılmaz.
- Doğrudan API isteğinde geçersiz alan 422 alır.
- Klavye ile skip-link ve form etiketleri kullanılabilir; axe WCAG A/AA
  taraması uygulanır. Bu tarama tüm erişilebilirliği tek başına kanıtlamaz.
- Metin %200 büyütüldüğünde form görünür ve sayfa yatay taşmaz.
- Sunucu gerçekten kaydettikten sonra yanıt kasıtlı kaybedilir. Tekrar
  gönderim aynı UUID için 200/replayed almalıdır. Tek satır kaldığı ayrıca
  veritabanından kontrol edilir.
- 15 saniyelik tarayıcı zaman aşımında belirsiz sonuç mesajı gösterilir,
  alanlar korunur ve düğme tekrar kullanılabilir.

Hata taklidi yapılan senaryolar depolama başarısı diye sunulmaz. Normal
gönderim ve yanıt kaybı senaryoları, doğru ortamla çalıştırıldığında gerçek
veritabanına gider.

8. YÖNETİM ERİŞİMİNİ KONTROL ETME

Bu bölüm yeni yönetim akışının kabul şartlarını tanımlar; güncel koşu
sonuçları üstteki kontrol kaydına işlenir.

- Oturumsuz /admin erişiminde giriş ekranı görülür; kayıtlar gösterilmez.
- Yanlış kullanıcı/parola genel hata verir; kayıt listesi veya çerez oluşmaz.
- Doğru demo girişinden sonra tablo açılır. Oturum çerezi HttpOnly,
  SameSite=Strict ve HTTPS'te Secure olmalı; ömrü bir saattir.
- UUID filtresi yalnız ilgili kaydı getirir; yenileme aynı satırı korur.
  Panelde dört alan, tarih, sayfalama ve salt okunur davranış kontrol edilir.
- Çıkıştan sonra kayıtlar okunamaz. Geçersiz veya süresi dolmuş oturum,
  kayıt API'sine erişim sağlamaz.
- Yabancı origin ile giriş/çıkış kabul edilmez.
- Aynı kaynaktan beş dakikadaki giriş denemeleri onla sınırlanır; sınırda
  429/yeniden deneme bilgisi beklenir.
- Veritabanı erişimi başarısızsa anlaşılır hata görünür; boş tablo
  gösterilerek başarılı okuma yapılmış gibi davranılmaz.
- Okuma token'ı ve parola özeti tarayıcıya veya hata yanıtına taşınmaz.
- Publishable key ile doğrudan tablo okuma/yazma yine reddedilir.
  Yönetim listeleme RPC'si doğru sunucu token'ı olmadan satır döndürmez.

Bu kontrolleri mevcut kullanıcı satırını değiştirerek veya silerek yapmayın.
